# Design

## Context

全新代码库，`openspec/specs/` 为空，无既有系统需要兼容。动机与范围见 `proposal.md`，各能力的行为契约见 `specs/`。

本机已就绪：JDK 17（Microsoft build）、Maven 3.9.16、MySQL 8.0.46、Redis 6.2.18、Node 24 / npm 11。未安装 Docker。

塑造本设计的三条外部约束：

- **运行环境是微信内置浏览器**，不是独立 App。一切交互必须在服务号网页授权的会话内完成。
- **上线期没有自动支付**。微信支付商户号与域名 ICP 备案均在申请中，首个可用版本只能依赖人工收款，但 2–3 周后必须能无痛切换。
- **规模极小**：10 位主播、数千粉丝、预期月订单数百笔。任何为万级并发设计的结构在此都是负债。

## Goals / Non-Goals

**Goals:**

- 支付手段可替换：从人工收款切到微信支付时，订单、分成、结算、埋点的代码一行不改。
- 金额与分账在任何时刻可复算、可对账，且历史数据不随配置变动而漂移。
- 订单不会"卡死"：任何一个等待状态都有明确的超时出口。
- 验证期所需的漏斗数据与业务数据同库同事务，不依赖第三方分析服务。

**Non-Goals:**

- 不做水平扩展、分库分表、读写分离、消息中间件。单体单库足以覆盖本期两个数量级的余量。
- 不做自动化退款。退款是人工动作，系统只负责产生队列与留痕。
- 不做前端服务端渲染与 SEO。页面只在微信内打开。
- 不追求对账全自动。运营每日核对流水是既定的人工流程，系统只负责把待办收敛到一个列表。

## Decisions

### D1 · 三端合一：单前端工程 + 单后端服务 + 单库

粉丝端、主播工作台、运营后台共用一个 Vue 工程（主播态与 `/admin` 均为路由分支）、一个 Spring Boot 服务、一个 MySQL 库。

**备选方案**：后台独立成第二个工程与服务。
**不采用的理由**：在 10 主播的体量下，独立后台意味着两套构建、两套部署、两套鉴权、两份模型映射，而收益（职责隔离）此刻为零。角色隔离用接口鉴权解决即可，不需要用部署边界解决。

### D2 · 支付做成 Provider 抽象，订单只消费"收款成功"事件

定义统一的支付端口，订单侧只认一个入站事件 `PaymentConfirmed(orderRef, paidAmount, provider, externalRef, operator?)`。

- `ManualPaymentProvider`：产出收款信息供展示，入口是运营在后台点"确认收款"。
- `WechatPayProvider`（后续）：产出 JSAPI 下单参数，入口是微信支付异步回调。

两者产出同一个事件，订单状态机对 provider 无感知。

**备选方案**：先把人工收款逻辑直接写在订单服务里，等接微信支付时再重构。
**不采用的理由**：这正是"2–3 周后切换不得返工"这条硬约束要防的事。抽象的增量成本只有一个接口和一个事件类型，而省下的是一次触及订单核心的重构。

**关键不变式**：`PaymentConfirmed` 必须幂等。以 `(orderRef, provider, externalRef)` 建唯一索引；重复事件被吞掉并留痕，绝不二次推进状态。微信支付回调天然会重投，这个约束现在就必须成立。

### D3 · 金额一律整数分；价格与分成在下单瞬间快照入单

所有金额字段用 `BIGINT` 存"分"，禁止浮点与 `DOUBLE`。

订单与打赏记录自带 `unit_price_cents`、`quantity`、`payable_cents`、`commission_rate_bp`（基点，万分之一为单位，避免百分比小数）、`guild_cents`、`talent_cents`。这些值在创建瞬间从配置读出并写死，此后任何配置变更都不回溯。

**备选方案**：结算时按当前配置实时计算。
**不采用的理由**：`service-pricing` 与 `settlement` 两份 spec 都把"调价/调比例不影响历史订单"列为必须。实时计算直接违反它，且会让财务永远对不平账。

**分账取整**：先算 `guild_cents = payable_cents * rate_bp / 10000` 向下取整，`talent_cents = payable_cents - guild_cents`。余数归主播，保证两项之和恒等于订单金额。

### D4 · 超时处置用 Redis ZSet 延时队列 + 兜底扫表

待支付超时与待接单超时各一条队列：订单进入等待状态时把 `orderId` 以到期时间戳为 score 写入 ZSet；一个单线程调度器每 10 秒取出到期成员处理。

同时保留一个每 5 分钟的兜底扫表任务，捞取"状态为等待中且已过期但仍在库里"的订单。

**备选方案**：只扫表，不用 Redis。
**不采用的理由**：只扫表会让超时精度等于扫描周期，而接单超时直接影响粉丝体验与退款量，精度需要到秒级。

**备选方案**：只用 Redis，不做兜底。
**不采用的理由**：Redis 重启或 ZSet 写入失败会导致订单永久卡在等待态——这是最糟的故障形态（用户付了钱、系统再不管它）。兜底扫表是廉价保险。

**幂等**：超时处置前以数据库乐观锁校验当前状态仍为预期的等待态，避免与主播接单的并发竞争。

### D5 · 时限参数随订单快照，不读实时配置

接单时限与待支付有效期都可由运营配置，但订单在创建时把当时的时限值写入自身的 `accept_deadline` / `pay_deadline` 绝对时间戳。

**理由**：`ordering` spec 明确要求"已在计时中的订单沿用其创建时的时限"。存绝对时间戳而非相对分钟数，还顺带让超时判定无需再读配置表。

### D6 · 埋点落本地事件表，不接第三方分析

`analytics_event` 单表，字段为 `event_key`、`user_id`、`talent_id`、`service_id`、`order_ref`、`occurred_at`、`props`（JSON）。前端在关键节点上报，后端在状态流转处直接写入。

漏斗看板用 SQL 按 `event_key` 做去重人数与相邻节点比值，不预聚合。

**备选方案**：接入友盟/神策一类第三方分析。
**不采用的理由**：本期要的是"付费转化"和"接单率"这类强业务语义指标，它们必须和订单表 join 才算得准；指标放在外部系统反而取不到。而且月事件量级在十万以内，直接查明细表毫无压力。

**写入必须不阻断业务**：事件写入异常只记录日志，绝不让异常冒泡到用户的下单请求上——`analytics-funnel` spec 对此有明确场景。

### D7 · 单用户多角色，而非多套账号

一个微信用户对应一条 `app_user`，其角色以位标记或关联表表达，可同时持有粉丝与主播角色。主播档案 `talent` 通过 `user_id` 关联到账号，但也允许暂时为空（运营可以先录入档案、后关联账号）。

**备选方案**：主播单独一套账号体系。
**不采用的理由**：主播本人也可能是粉丝，且都从同一个服务号进入，分账号会立刻产生"用哪个身份登录"的困惑，徒增复杂度。

### D8 · 订单号采用时间前缀 + 随机后缀

格式 `yyMMddHHmmss` + 6 位随机数字，共 18 位。便于运营在对公账户流水与订单之间人工比对（这是上线期每天都要做的动作），同时避免自增 ID 泄露交易量。

### D9 · 支付凭证存对象存储，库里只存引用

凭证图片上传至对象存储，`payment_proof` 表记录 URL、上传时间、上传者与所属订单。同一订单允许多条凭证记录，全部保留供运营核对——`payment` spec 要求重复上传不覆盖。

## Risks / Trade-offs

- **域名 ICP 备案延期** → 这是唯一能让 4 周工期白做的外部因素。备案与开发完全并行，第一天就提交；开发期全程用内网穿透或测试域名联调，不等备案。
- **主播接单率低于 80%，导致转化率数据失真** → 系统侧的对策是把接单率做成独立指标并带阈值告警（见 `analytics-funnel`），让这个问题在第一周就暴露而不是到复盘时才发现。但根因是分成比例，属于商务动作，系统只能观测不能解决。
- **人工对账成为吞吐瓶颈** → 月数百笔时每日十几分钟可接受。对策是把待对账做成单一收敛列表并支持按金额快速检索；真正的解法是尽快切微信支付，这也是 D2 存在的理由。
- **支付凭证可伪造** → 本期不做图像识别。对策是运营以对公账户实际到账流水为唯一准绳，凭证只作辅助定位；`payment` spec 的"驳回"场景即为此设计。
- **抽象层带来的额外复杂度** → 为一个只有一种实现的接口付出设计成本。接受，理由见 D2。
- **单体单库的单点故障** → 本期接受。数据库每日备份，服务异常时订单处于等待态而非丢失，可人工恢复。

## Migration Plan

本次为全新系统，无数据迁移。需要规划的是**支付方式的在线切换**：

1. 上线时 `manual` 为唯一启用的 provider。
2. 微信支付商户号下发后，接入 `WechatPayProvider`，以灰度开关在后台启用，两种方式并存。
3. 观察一周，确认回调幂等与对账无误后，将 `manual` 降级为仅运营可见的兜底通道（用于处理微信支付失败的个案）。
4. 回滚策略：任何一步出问题，在后台关闭 `wechat` provider 即可退回纯人工收款，订单侧无需改动与发版。

## Open Questions

- 公会分成比例与各档位具体定价尚未与公司确定。不影响设计与任务拆分——二者均为后台配置项，上线前填入即可。
- 接单时限的具体分钟数（初值暂定 15 分钟）与待支付有效期的具体时长，待首周真实数据出来后调整。二者均为可配参数，不影响实现。
