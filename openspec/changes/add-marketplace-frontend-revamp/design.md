# Design

## 背景与定位变化

上一个 change 按「私域收银台」实现：粉丝指名下单，不存在匹配问题，因此刻意不做发现与互动。本次把定位改为撮合平台，发现链路从无到有。这不是加几个页面，而是引入了三类此前不存在的东西：

1. **UGC**——动态、评论、站内消息。平台从此承担内容审核义务。
2. **虚拟权益**——优惠券、元子余额。账务必须可追溯、可对账。
3. **排名与等级**——打赏榜、粉丝等级。涉及周期性计算与固化。

这三类各自的失败模式不同，下面分别处理。

## 关键决策

### 元子只记账，不开放充值

真实充值会形成预付资金沉淀，这是微信支付商户审核与资金监管最敏感的部分，且一旦开放再收回极难。本次只做账务骨架：余额、流水、运营手工调整。充值入口在前端完全不存在，不是隐藏，是不实现。

账务用与金额一致的做法：整数记录，每笔变动必须产生流水，流水记录变动后余额以便对账。余额扣减走乐观锁，不允许出现负余额。

### 优惠券的抵扣由公会承担，分成基于原价

这是本次最容易出错的地方。券是公会的促销手段，不应由主播承担成本。因此订单需要同时记录**原价**与**实付**：

- 分成基于原价计算，主播到手不受券影响
- 券的抵扣额计入公会的促销成本
- 结算报表需新增一列区分这两者

如果按实付分成，主播会因为公会发券而无故减收，这会直接破坏主播关系。

### 榜单用周期快照，不实时算

日/周/月榜如果每次查询都实时聚合打赏流水，随数据量增长会越来越慢，且周期切换的边界难以界定。采用：当前周期实时累计（增量更新），周期结束时固化为快照。已固化的历史榜单只读。

退款需要从累计中扣除，因此累计值必须可增可减，不能只累加。

### 随机匹配不是抽奖

这一条写进 spec 是刻意的。随机匹配与抽奖的区别在于：匹配不收费、不消耗次数、结果不是奖品。只要这三条守住，它就是随机派单，不涉及射幸。一旦给匹配本身收费或加入「稀有度」，性质立刻改变。实现上要确保匹配接口无任何扣费分支。

### UGC 的审核义务

引入动态、评论、站内聊天后，平台需要能举报、能下架、能追溯。下架必须是软下架：对粉丝不可见，但原始内容与处置记录保留。硬删除会让纠纷无从查证。

站内消息不允许单方撤回已送达的消息，原因同上。

## 数据模型

### 变更已有表

- `talent`：新增 `gender`、`age`、`region`、`promo_tag_1`、`promo_tag_2`。
  全部可空——现有 34 条记录没有这些值，不能设非空约束。
- `service_order`：新增 `original_amount_cents`（原价）、`coupon_discount_cents`（券抵扣）、`coupon_id`。
  现有订单回填为 `original_amount_cents = amount_cents`、抵扣为 0。

### 新增表

| 表 | 用途 | 要点 |
|---|---|---|
| `talent_favorite` | 收藏 | `(user_id, talent_id)` 唯一索引保证幂等 |
| `audition_request` / `audition_reply` | 试音需求与应征 | `(request_id, talent_id)` 唯一索引 |
| `moment` / `moment_image` / `moment_like` / `moment_comment` | 动态 | 点赞唯一索引；动态软下架标记 |
| `content_report` | 举报 | 多态关联（动态/评论/消息） |
| `chat_conversation` / `chat_message` | 站内聊天 | 会话按 `(fan_id, talent_id)` 唯一 |
| `tip_rank_current` / `tip_rank_snapshot` | 榜单 | 当前周期可增减，历史只读 |
| `user_level_rule` | 等级门槛 | 后台可配 |
| `coupon` / `user_coupon` | 券与券包 | `user_coupon` 记录领取、使用、退回 |
| `credit_account` / `credit_transaction` | 元子 | 流水记录变动后余额 |
| `home_block_config` / `home_banner` | 首页可配位 | 含生效时间 |

沿用既有约定：不用外键，金额整数分，`DATETIME(3)`，布尔用 `TINYINT(1)`。

## 不做与理由

- **电竞分区**：引入业务分区会让服务目录、价格、筛选全部多一个维度，改动面远超收益。表结构预留 `category_id` 但不启用。
- **用户充值与提现**：见上。
- **营销文案模板与封面烧字**：系统只提供字段与审核开关。竞品把「打赏15+v」这类文案做成卖点，那是运营选择，不应由系统固化为功能。
- **主播端与运营后台视觉改版**：内部工具，能用优先。

## 风险

| 风险 | 影响 | 处置 |
|---|---|---|
| UGC 内容违规 | 平台承担审核责任，严重时账号与支付通道受影响 | 举报入口 + 运营下架 + 全量留存；上线初期可先只放开主播发布，粉丝只读 |
| 券成本失控 | 公会实际毛利被侵蚀 | 券需设发放总量与单用户限领；结算报表单列促销成本 |
| 范围过大一次上线 | 质量与工期同时失控 | tasks 按组分批，第 1~3 组构成可独立上线的最小集 |
| 新增入口无人使用 | 开发投入无回报 | 每个入口独立埋点，上线后按入口归因砍掉无效入口 |

## 待定（不阻塞开发）

- 等级门槛的具体数值、券的面额与门槛档位——后台可配，由运营在上线前填。
- 心动墙的筛选规则——先做成运营手工挑选，跑一段时间再定规则。
