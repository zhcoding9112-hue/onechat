# 分账口径与取整规则

本文说明每一笔钱是怎么算出来的。**按本文手工复算，结果必须与系统输出一致**；
对不上就是 bug，不是口径理解不同。

## 两条铁律

1. **金额一律取来源上的快照**。订单与打赏在创建瞬间把单价、数量、应付金额、分成比例
   全部写死在自己身上，此后运营怎么改配置都不回溯。结算只读这些快照，绝不读当前配置。
2. **全程整数分，不出现浮点**。金额用 `BIGINT` 存「分」，比例用 `INT` 存「基点」
   （万分之一）。`0.1 + 0.2 != 0.3` 这种误差在财务上是不可接受的。

## 计算公式

设来源金额为 `A`（分），分成比例为 `R`（基点）：

```
公会分成 = floor(A × R / 10000)
主播应得 = A − 公会分成
```

**取整规则：公会向下取整，余数归主播。** 两条理由：

- 两项之和恒等于 `A`，财务永远对得平，不会出现一分钱的长期漂移。
- 不能整除时那一分给主播而不是公会——主播对到手金额敏感，公会不在乎一分钱。

### 手算示例

| 来源金额 | 比例 | 公会分成 | 主播应得 | 说明 |
| --- | --- | --- | --- | --- |
| 10000 分（¥100） | 3000（30%） | 3000 | 7000 | 能整除 |
| 9999 分（¥99.99） | 3000（30%） | 2999 | 7000 | 9999×0.3 = 2999.7，向下取整 2999 |
| 1 分 | 5000（50%） | 0 | 1 | 0.5 向下取整为 0，那一分归主播 |
| 3333 分 | 3333（33.33%） | 1110 | 2223 | 3333×0.3333 = 1110.89 |
| 8800 分（¥88） | 3000（30%） | 2640 | 6160 | |

验证方式：`公会分成 + 主播应得` 必须恒等于来源金额。

## 什么计入结算

| 来源 | 计入时点 | 说明 |
| --- | --- | --- |
| 服务订单 | 主播标记完成时 | 待接单、已接单、已超时的订单都不计入 |
| 打赏 | 运营确认收款时 | 打赏没有接单与完成，确认收款即完成 |

**不计入的情况：**

- 已超时的订单。钱虽然收到了，但服务没发生，会走退款。
- 已取消的订单与打赏。
- 已退款的订单与打赏。若退款前已记过账，该记录被**冲销**而非删除——
  删掉就查不到"这笔钱曾经算过账"，纠纷时无从追溯。冲销后的记录状态为 `REVERSED`，
  不计入任何报表合计，但在明细导出里仍然可见。

## 台账

`settlement_entry` 是财务的唯一依据。关键约束：

- `(source_type, source_id)` 唯一。同一笔订单或打赏只能记一次账，重复生成被数据库挡住，
  而不是靠应用层「先查再写」——并发下先查再写挡不住。
- `occurred_at` 是业务发生时间（订单的完成时间、打赏的收款时间），报表按它归集到周期。
  用它而不是记录创建时间，是为了让跨月补记的账仍然落在正确的月份。

## 报表

按自然月、按主播出表。每行包含：

- 服务订单金额、打赏金额（两者分列，便于观察收入构成）
- 公会分成、主播应得
- 订单数、打赏数
- 是否已线下结清

**周期内没有任何流水的主播也会成行，各项为零。** 不是缺行——否则运营核对时
会漏掉「这个月这位主播一单没有」的情况，而那恰恰是需要关注的信号。

## 结清标记

系统**不提供**站内提现、打款或资金划转。分成只是记账，实际支付走公会既有的线下月结。

运营在报表上把某主播某周期标记为「已线下结清」，系统只记录这个标记、操作者与时间，
不发生任何资金动作。标错了可以撤销。

## 常见核对路径

月底对账时：

1. 导出当月报表（`/api/admin/settlement/report/export?period=yyyy-MM`）
2. 对金额有疑问的主播导出逐笔明细（`/api/admin/settlement/entries/export`）
3. 明细里的每一行都能用上面的公式手算验证
4. 明细中「已冲销」的行不计入报表合计，核对时跳过即可

导出为 CSV 且带 BOM，用 Excel 直接打开不会乱码。
