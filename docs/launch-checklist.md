### A2. 订单时限被改成了 1 分钟 — 已处理（2026-11-20）

```
处理前: pay_minutes = 1,  accept_minutes = 1
处理后: pay_minutes = 30, accept_minutes = 15   ← 与迁移里的默认值一致
```

我在验证超时链路时手改成 1 分钟，没改回去。带着那个值上线，粉丝下单一分钟内
没付款就被自动取消，主播一分钟没接单订单就超时进退款队列——没人能正常完成一单。

已按你的指示改回：

```sql
UPDATE order_deadline_setting SET pay_minutes = 30, accept_minutes = 15 WHERE singleton_key = 1;
```

30 / 15 是迁移里的默认值，不是我新挑的数。**这次是恢复默认才直接改的库；
日后要调请走运营后台**（`PUT /api/admin/orders/deadlines`），那条路径带正数校验与操作日志。

改动只影响此后创建的订单。库里那一笔 `PENDING_CONFIRM` 的订单不受影响——
时限在下单那一刻就折算成绝对时间戳写进订单自身了。

### A3. 首页九宫格与横幅全部指向「/」

九个运营位（6 个九宫格 + 3 个横幅）的 `target_url` 全是 `/`，`image_url` 全为空。

其中一条横幅标题是**「已过期的活动」**，而 `enabled = 1`——它现在就挂在首页上。
另一条「新人首单立减」承诺了一张券，而券表里一张券都没有（`SELECT COUNT(*) FROM coupon` = 0）。

要么把目标地址和图配齐，要么先把这九条停用。承诺了拿不到的优惠，比没有运营位更糟。

核对：`SELECT entry_type, title, target_url, enabled FROM home_entry ORDER BY entry_type, sort_order;`

### 这些数据从哪来

有几个测试类**刻意不加 `@Transactional`**——它们要验的就是真实提交下的行为
（事务传播、唯一索引幂等、并发），套一层测试事务什么也验不到。代价是造出来的
数据不回滚，必须自己清。

`AnalyticsResilienceTest` 此前没有自清，每跑一次就漏四个**已上架**的主播和四个
服务项目。开发库里 113 个叫「小雨」的主播全是它留下的。**这个已经修了**
（`@AfterEach` 按引用方向删回去）。

修完跑一轮 703 项全量测试复核：「小雨」仍是 113 个，没有新增——这一条漏算堵上了。
主播总数仍涨了 14 个，全部 `listed = 0`，来自另外几个并发测试（见 E 节），
粉丝端看不到它们。**现在起不会再有新的已上架测试主播进库。**

### 清理脚本

`scripts/cleanup-test-data.sql`，先盘点后删除，不带确认标记只盘点不删：

```bash
mysql -u root private_checkout < scripts/cleanup-test-data.sql
```

确认数字无误后再真删：

```bash
mysql -u root private_checkout -e "SET @CONFIRM='YES'; SOURCE scripts/cleanup-test-data.sql"
```

判定规则靠命名（测试夹具的 open_id / code / nickname 一律带 `System.nanoTime()`
后缀），不靠创建时间，所以脚本可以反复跑。

脚本会**保留**这些账号，执行前请自己扫一眼确认里面只有真人与本机调试桩：

| id | open_id | 说明 |
| --- | --- | --- |
| 12317 | `olcEa3...` | 理查德，真实微信授权登录过的账号 |
| 84 / 1302 / 3079 / 8220–8224 | `stub_*` | 本机联调用的假登录账号 |

`stub_*` 这八个在上线前也该删——它们是本机调试桩，线上不需要。脚本没动它们，
是因为你本机还在用。

## D. 需要运营补齐的内容

### D1. 主播花名册（先更正一个说法）

我之前反复说过「34 位主播缺封面」。**这个说法不准确**，得更正：34 是
`tasks.md` 里记的、公会计划签约的人数，不是库里的行数。库里现在只有两条
开发期演示数据（小雨、阿澈），清理完测试数据后，**主播表基本是空的**。

也就是说这不是「补图」，是**整个花名册要从头录**：昵称、性别、年龄、地区、
简介、封面图、试听片段、宣传语标签、服务项目与价格。

前面十二组做的发现链路——品类筛选、人气店员、试音选人、随机匹配、心动墙、
榜单——全都要有人才有东西可发现。这是上线前工作量最大的一项，也最该早点开始。

### D2. 等级门槛与名称仍是占位值

```
L1 / 0 元        L2 / 200 元      L3 / 1000 元
L4 / 3000 元     L5 / 10000 元
```

所以不改也不会算错钱——但粉丝会看到自己是「L3」。

后台可改：运营后台 → 粉丝等级。

### D3. 券的面额与门槛档位未定
