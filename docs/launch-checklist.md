### A2. 订单时限被改成了 1 分钟 — 已处理（2026-11-20）

```
处理前: pay_minutes = 1,  accept_minutes = 1
处理后: pay_minutes = 30, accept_minutes = 15   ← 与迁移里的默认值一致
```

我在验证超时链路时手改成 1 分钟，没改回去。带着那个值上线，粉丝下单一分钟内
没付款就被自动取消，主播一分钟没接单订单就超时进退款队列——没人能正常完成一单。

已按你的指示改回：

```sql
UPDATE order_deadline_setting SET pay_minutes = 30, accept_minutes = 15 WHERE singleton_key = 1;
```

现在这两个值在后台可以直接改了：菜单「订单管理」→「订单时限」页签。
**改动只影响此后创建的订单**——已经在计时中的订单，在创建时就把时限折算成
绝对时间写进了自己身上，不会被追溯修改。

30 / 15 是迁移里的默认值，不是我新挑的数。**这次是恢复默认才直接改的库；
日后要调请走运营后台**（`PUT /api/admin/orders/deadlines`），那条路径带正数校验与操作日志。

改动只影响此后创建的订单。库里那一笔 `PENDING_CONFIRM` 的订单不受影响——
时限在下单那一刻就折算成绝对时间戳写进订单自身了。

### 这些数据从哪来

有几个测试类**刻意不加 `@Transactional`**——它们要验的就是真实提交下的行为
（事务传播、唯一索引幂等、并发），套一层测试事务什么也验不到。代价是造出来的
数据不回滚，必须自己清。

`AnalyticsResilienceTest` 此前没有自清，每跑一次就漏四个**已上架**的主播和四个
服务项目。开发库里 113 个叫「小雨」的主播全是它留下的。**这个已经修了**
（`@AfterEach` 按引用方向删回去）。

### 清理顺带暴露了三条「靠垃圾数据才绿」的测试

清理后首次跑全量测试，三条立刻红了：

| 测试 | 为什么红 |
| --- | --- |
| `RandomMatchTest.连续匹配不是固定顺序或轮询` | 不自己造候选，直接依赖库里恰好有一堆已上架主播；只剩 2 位时随机性无从体现 |
| `RandomMatchTest.连续换五位互不相同` | 同上，需要至少 5 位候选 |
| `HomeBlocksTest.分页不重不漏` | 第二页为空，AssertJ 对空集合直接抛参数异常 |

**这不是清理造成的，是清理暴露的。** 它们一直靠别的测试漏下来的垃圾数据才通过——
换一台干净的机器、或者新同事第一次拉代码跑测试，一样会失败。
三条都已改成自己造够数据，不再依赖环境里恰好有什么。清理后 703 项全绿。

### 清理脚本

`scripts/cleanup-test-data.sql`，先盘点后删除，不带确认标记只盘点不删：

```bash
mysql -u root private_checkout < scripts/cleanup-test-data.sql
```

确认数字无误后再真删（`SOURCE` 是 mysql 客户端内建命令，不能跟在 `-e` 后面，
只能走标准输入）：

```bash
{ echo "SET @CONFIRM='YES';"; cat scripts/cleanup-test-data.sql; } | mysql -u root private_checkout
```

判定规则靠命名（测试夹具的 open_id / code / nickname 一律带 `System.nanoTime()`
后缀），不靠创建时间，所以脚本可以反复跑。脚本末尾还会扫一遍孤儿行——
开发库里就有一条指向早已不存在的主播的价格行，按「测试主播」那条规则是删不掉的。

脚本会**保留**这些账号：

| id | open_id | 说明 |
| --- | --- | --- |
| 12317 | `olcEa3...` | 理查德，真实微信授权登录过的账号 |
| 84 / 1302 / 3079 / 8220–8224 | `stub_*` | 本机联调用的假登录账号 |

`stub_*` 这八个在上线前也该删——它们是本机调试桩，线上不需要。脚本没动它们，
是因为你本机还在用。

## E. 已知、但判定为低危的遗留

列在这里是为了你知道它们存在，不是建议现在动。

- **另外五个并发测试会留下「已下架」的主播行**（库里 51 条带数字后缀的）。
  它们 `listed = 0`，粉丝端看不见，只在运营后台的主播列表里碍眼。
  我没顺手改，是因为每个都要连带处理价格、标签等关联行，改五处的风险
  大于它带来的麻烦；清理脚本会一并删掉这些残留。
- **分成比例 30%**（`commission_config.rate_bp = 3000`）是上一个 change
  定的默认值。若与实际约定不符，在运营后台改——注意**改动只影响此后的新订单**，
  已有订单的分成在下单那一刻就快照了，不会被追溯修改。
- **接单率告警阈值 80%**（`analytics_setting`）来自 proposal 的建议值，
  可按实际情况在看板上调。
- **打赏没有超时回收。** 超时任务（`OrderTimeoutScheduler`）只处理服务订单；
  打赏虽然也有支付截止时间，到点后没有任何东西去关它。粉丝发起却不付款的
  记录会一直挂在后台「打赏管理 → 待处理」里，只能手工点「取消」清掉。
  补上这段补的是后端定时任务，不是页面，所以这次没做。
  量不大时手工清就行；量上来了再说。
- **打赏与订单列表都没有分页，也没有搜索。** `GET /api/admin/tips` 与
  `GET /api/admin/orders` 一次把该状态的全部记录返回，「打赏管理 → 记录」和
  「订单管理 → 全部订单」两页随记录增长会变慢。订单页的关键字框是在**已加载的
  列表里**本地过滤，不是服务端搜索——记录多了之后它找不到没加载进来的单。
