#### 关于 `stub_*`：我之前的说法要更正

我写过「这八个在上线前也该删」。**这句话是错的**，得更正两点：

**一、它们根本到不了线上。** 按 `docs/deploy.md`，生产是 `CREATE DATABASE` 建一个
空库再让 Flyway 迁移，不是把本机这个库导过去。这些行只存在于你这台机器上。
真正的防线也不是删行，而是：prod profile 下没配 `WECHAT_APP_ID` 会**直接启动失败**，
不会退化成授权桩（见 `StubWechatOAuthClient` 的注释）。那一条已经在了。

**二、删 `stub_local_dev` 会把你自己关在后台外面。** 角色是位标记：

| 账号 | roles | 含义 |
| --- | --- | --- |
| `stub_local_dev` | 5 | FAN + **OPERATOR** |
| `stub_talent_user` | 3 | FAN + TALENT，绑着主播「小雨」 |
| 理查德（真实微信号） | 1 | 只有 FAN |

`AppUserService.registerOrUpdate` 给新用户的是 `Roles.DEFAULT`，也就是只有 FAN；
而所有后台接口都挂着 `@RequireRole(OPERATOR)`，**代码里没有任何授予 OPERATOR 的接口**。
所以删掉 84 之后重新登录会建出一个新号，但它只有 FAN，进不去后台，
而理查德也只有 FAN——整个库里就没有运营账号了，只能手写 SQL 才能救回来。

另外本机的授权桩 `buildAuthorizeUrl` 把 code 写死成 `stub_local_dev`，
所以正常流程登录**只会**登成 84 这一个号。

**2026-11-22 删掉了其中六个**：`stub_pure_fan` 和 `stub_fnl0`–`stub_fnl4`，
它们 roles 都是 1、不绑任何数据，走正常流程也登不到，删了零成本。
留下 84 和 1302 两个：前者是你进后台的唯一钥匙，后者绑着主播「小雨」
（`talent.user_id`），删了小雨的主播工作台就断了。

这两个要删的话，得先决定谁来当运营——比如把 OPERATOR 授给理查德那个真实微信号
（目前没有界面，得 `UPDATE app_user SET roles = roles | 4 WHERE id = 12317`）。

#### 2026-11-22：加了批量导入，但名单本身仍然等你

一个一个在表单里敲三十几个人太慢，所以在「主播管理」加了 **批量导入**：
下载 CSV 模板，填好，先点「试算」再点「正式导入」。

- 模板表头固定：`昵称,性别,年龄,地区,简介,标签,宣传语,排序,服务档位,价格元`
- 标签和宣传语一格里填多个，用 `|` 分隔
- 一次最多 500 行
- **试算**只校验不写库，把每一行的问题列出来；有任何一行不合法，**整批都不导入**，
  不会出现「前八行进去了、第九行报错」这种一半的状态
- 导入进来的主播**一律是未上架**。封面和试听是逐个传的文件，导入带不进来，
  自动上架等于把没有封面的人推到首页

**导入不会凭空造出名单。** 昵称、年龄、地区、简介、价格这些得是真人的真实信息——

上线前跟着演示数据一起处理。

接单后就能直接标完成；包天包周需要跨天的履约状态，不在本期范围内。
真要做，得先把状态机改回来。

### D2. 等级门槛与名称 — 已定（2026-11-21）

原本五级都叫「L1」到「L5」。**2026-11-21 已改成有意义的名字**：

```
新客 / 0 元      常客 / 200 元    银卡 / 1000 元
金卡 / 3000 元   黑卡 / 10000 元
```

门槛也一并调低了（原来是 200 / 1000 / 3000 / 10000）。原因：按 ¥20–50 一单算，
旧的「黑卡」要三百单以上，等于没人够得着——够不着的等级没有任何激励作用。
新的一档按「十来单升一级、再翻四倍」排，常客约 5 单、银卡约 20 单、
金卡约 60 单、黑卡约 200 单。

名字走零售会员卡那套中性叫法，没有任何暧昧暗示。等级只影响展示，不影响下单
价格与分成，所以叫什么、门槛多少都不会算错钱——但粉丝会看到。
**这是我替你定的，不合适就改**：运营后台 →「粉丝等级」。

### D3. 券的面额与门槛档位 — 已定（2026-11-21）

原来券表是空的，而首页横幅在喊「首次下单立减 **20** 元」。这两件事对不上，
而且**那个数字本身就不可能成立**。

先把账算清楚。分成是 30%，一笔原价 X 的订单：

```
公会分成 = 0.30X      主播应得 = 0.70X      券的钱由公会出，不从主播那里扣
公会实得 = 0.30X − 券面额
```

所以**券面额一旦超过订单原价的 30%，公会在这笔单上就是亏的**。
按现在 ¥15 / ¥25 的演示价，「立减 20 元」要么用不上，要么让公会倒贴。

定的档位是「面额 ≈ 门槛的 15%」，也就是**只让出公会分成的一半**：

| 券 | 门槛 | 面额 | 相当于 | 这一单公会实得 |
| --- | --- | --- | --- | --- |
| 新人首单券 | 满 ¥20 | 减 ¥3 | 15% | ¥6 − ¥3 = ¥3 |
| 满 50 减 8 | 满 ¥50 | 减 ¥8 | 16% | ¥15 − ¥8 = ¥7 |
| 满 100 减 15 | 满 ¥100 | 减 ¥15 | 15% | ¥30 − ¥15 = ¥15 |

**横幅文案已改成「首单满 20 减 3」**，跳转指向「我的券」，
三档券已向当时库里的全部用户发放，**横幅也已开启**（2026-11-21）。

**新注册的用户会自动拿到新人券**（2026-11-21 补上）。

此前发券只有「全体发放」，是一次性快照——执行那一刻库里有谁就发给谁，
之后注册的人拿不到，横幅写着「新人首单立减」而真正的新人点进去是空券包。
现在每张券上多了一个「注册即发」开关，打开后新用户一建号就拿到。

**只有「新人首单券」打开了这个开关**，满 50 / 满 100 那两张没开——
它们是促销券，不该人人进门就送。

开关在后台「优惠券」列表里，每行一个。打开时会提醒一句：
**这是持续支出，不是一次性发放**；关掉之后注册的人就不再拿到，
但已经发出去的不会收回。已经注册过的人要补发，还是用「发放」。

系统本身有一道保险：券面额不得超过门槛（建 ¥20 面额 / ¥15 门槛的券会被拒），
所以实付永远不会被减成负数。但它拦不住「面额超过分成」这种亏本档位，
那条线得你自己守。

真实价目定下来后回头核一遍这三档：门槛要落在你最常成交的价位附近才有用。
